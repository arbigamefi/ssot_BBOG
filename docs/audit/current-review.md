## 2. 新发现及未关闭事项

### F01 · P1 · 极小赎回会使未退出 LP 的资本停止周转

这是本轮最重要的设计问题。[Bank.activateBatch](../../src/core/Bank.sol) 无论赎回比例多小，都把当前全部准备金转入 `recoveryBacking`。旧仓终结后，`_chargeEpochHold` 将释放价值保留为所有原持有人的领取权，不恢复活跃 NAV。留存 LP 必须 `claimRecovery` 后另外 `deposit` 才能继续用这部分资本承保。

在当前真实 Bank 的独立本地 Anvil 上复现，并由主审再次重跑：

1. 原 LP 存入 100 USDC，此后一直保留全部份额，不申请退出。
2. 每一轮另一个账户只入金并申请赎回 0.000001 USDC；有一笔 20 USDC 投注，占用 40 USDC 准备金。
3. 到期激活请求，领取该微小请求的现金，再把那笔投注全额退款。连续四轮。
4. 四轮均完全终结，无玩家损益、协议费或未结准备金。

| 状态     |  Bank 现金 |  活跃 NAV | 历史回收 backing | 未结仓位 |
| -------- | ---------: | --------: | ---------------: | -------: |
| 开始     |        100 |       100 |                0 |        0 |
| 四轮结束 | 100.000004 | 20.000004 |               80 |        0 |

此时同样的 20 USDC 投注因 `SolvencyViolation()` 被拒绝。原 LP 领取 79.999996 USDC 并重新存入后，NAV 恢复 100，同一投注又可接受。两条路径没有其他资本注入。复现共 39 笔成功交易；另一个正常亏注结算场景也得到资本被动闲置的结果。

证据边界：使用真实 Bank、精确转账的 6 位 MockERC20、具有路由权限的本地账户，风险缓冲 1,000 bps；准备金比例对应 CoinToss 的两倍 stake。没有在完整 GameHub/VRF 路径执行这个反例，也没有证明所有大小的投注都会停止。

这不表示资金被盗或资不抵债。它表示**“没有调用 pause”仍不足以实现用户要求的持续下注**。未退出者的本金在没有亏损时，因为别人的微小赎回而被动停止承保。当前实现符合 ADR-0035，所以必须补齐设计验收要求，不能只修改文案。

原评审约束（Owner 后续已调整，见第 5 节）：旧风险及回收权仍归原持有人，后来入金者不能取得旧权益，永久旧仓仍不能阻塞后续退出；同时，正常结清后留存资本应继续周转。不能直接把所有回收款加回当前 NAV；不能用 keeper operator 授权或要求所有 LP 定期手动领取再存入代替解决设计问题。

新增差分验收：同样的本金和全额退款投注，比较“无赎回”与“极小赎回”路径。全部终结后，承保能力的差异只能来自实际退出、费用及规定的舍入，不能来自未退出 LP 被动变成领取款持有人。

### F02 · P1 · 前端执行地址未完整绑定到认证快照

[严格验证器](../../script/release/validate_frontend_artifacts.py) 第 323–325 行比较 sports、pools 和 vectors，却没有比较 `manifest.addresses`、`manifest.games` 与 snapshot。[ssot-sync](../../frontend/scripts/ssot-sync.mjs) 第 349–358 行随后直接用 manifest 地址生成运行时配置。投注 SDK 会向其中的 GameHub 发送调用和原生币费用。

实测：仅将 `manifest.addresses.gameHub` 从 `0x…01` 改成 `0x…63`，release 和 snapshot 的哈希保持不变，`--strict 1` 验证仍返回 0，正常对照也返回 0。主审独立重跑得到同样结果。

这次动态证据是**严格验证器层面的接受错误地址**，样本没有有效发行签名，也未执行带真实链上治理状态的完整导入。完整调用链源码显示，后续签名及治理验证只消费 release/snapshot，没有再认证 manifest 中的执行地址；应以完整、有效签名的本地导入反例补齐端到端证据。

修复目标：所有被消费者用于执行交易的地址、游戏映射及相关配置都必须来自认证快照或与之逐字段严格一致。任何不一致必须在写入 active release 前失败；不能以文件格式正确、地址非零或 ABI 哈希正确替代身份认证。

### F03 · P2 · 玩家应付款自动领取缺少可靠恢复与告警

实际加载当前 [payables.ts](../../frontend/apps/keeper/src/payables.ts) 和 [health.ts](../../frontend/apps/keeper/src/health.ts)，复现三个缺口：

- **领取被重组撤销后漏重试。** 旧创建事件位于 block 20，head 100 时领取成功便删除玩家；模拟领取交易被浅重组撤销、欠款恢复为 5，head 102 连续运行四次，仍显示 `caughtUp=true, pending=0`，没有重新领取。创建事件已在 24 区块回扫窗口之外。玩家仍能自行领取，重启全量重放也能恢复；链上债务没有丢失。
- **小扫描预算原地打转。** 合法配置 chunkSize=10、maxChunks=1、origin=10、head=100，十轮都只扫描 10–19，发现不了 block 50 的欠款。原因是每轮回退 24 区块再应用预算。默认 10×50 不触发此特定停滞；现有历史回收扫描器已经有可复用的推进方式。
- **发现故障仍显示正常。** 上述落后及独立 RPC 错误在 `recordPayables` 后仍为 `status=running`。应区分发行方拒付的正常退避和扫描/游标故障，后者需要可见告警。

这些是实际模块配合可控链响应的复现，没有在真实分叉链制造重组。修复应保留成功领取及零余额观察的重组恢复信息，确保有限扫描预算仍单调推进，并测试故障告警及恢复清除。

### F04 · P2 · 正式发布工作流没有发布包输入

[Release Gate](../../.github/workflows/release.yml) checkout 后直接执行 `STRICT=1 make release-check`。当前 `deployments/` 被忽略且没有受版本控制的产物，workflow 没有下载或生成该发布包的步骤。严格命令在当前干净候选上实际失败：`missing release artifact: deployments/release-latest-v16.json`。

因此包内不含当前审计范围承诺的 SDK、keeper、indexer、UI；严格产物验证也缺输入。部署前源码审计应直接围绕完整提交、依赖锁、ABI 和对应验证证据组包，部署后的链上材料再附加；不需要再建一套兼容或迁移系统。

### F06 · P2 · 白皮书对治理权限有两处过度承诺

[技术白皮书](../WHITEPAPER.zh-CN.md) 第 243 行称治理不能改写已接受投注的条件，但 [GameHub](../../src/core/GameHub.sol) 的 `setRefundTimeout` 即时更新全局值，`refund` 第 575 行对旧投注使用当前值。接受时为 1 小时、后来改成 1 天，就会改变旧投注退款时点。一次性 `registerGame` 不能证明所有条件都已冻结。

第 242 行称 guardian 只能暂停新风险；实际暂停还阻止 LP 批次激活、现金领取和回收领取。玩家结算及应付款领取仍可继续。ADR 与 SSOT 对此写得更准确。

先明确哪些接受条件必须冻结、哪些运营参数允许影响旧投注，再统一代码与承诺。当前有界的全局退款超时本身不应直接定性为攻击漏洞。另已确认：撤销 Hub 准入或停用 pool 不会阻断 Router 对既有仓位的合法终结。

### F07 · P2 · 收益显示缺少份额转移的成本依据

[BankProviderLedgerPanel](../../frontend/apps/web/src/features/earn/BankProviderLedgerPanel.tsx) 第 66–77 行用“领取 + 当前权益 − 入金”显示净 P&L。但普通 LP 份额可以转账，现金账本只收集 Deposit、Withdraw、RecoveryClaimed。

实际组件渲染反例：收到价值 100 USDC 的份额、没有自己的入金事件，会显示净 P&L +100 USDC；这不是池子的经营利润。当前 PG 不完整覆盖分支会隐藏该指标，RPC 完整回溯分支则可以触发。没有完整权益转入/转出依据时应隐藏收益或明确显示为账本差额，不必为这个展示新增成本基础系统。

### F08 · 验收缺口 · 真实合约与钱包路径没有成为自动门禁

四项 Anvil SDK 测试仍通过 `skipIf(!BANK_ANVIL_RPC)` 默认跳过；Frontend CI 没有启动 Anvil，路径过滤也不包含单独的合约或编译配置变更。附件已经记录它曾漏掉 offset 修改后的失效断言。

现有浏览器检查是页面、无障碍和移动钱包跳转，不是连接钱包后的资金闭环。应增加一个本地完整流程：存入 → 请求 → 持续下注 → 激活 → 后续 LP 退出 → 钱包份额归零后领取现金/旧权益 → 玩家应付款重试，并覆盖恢复与账户/链切换。

### 已接受的 F01 规则与当前实现

Owner 已明确采用：**只冻结退出者旧权益，留存份额持续承保；新入金按包含未结投注本金的完整账面价买入剩余活跃风险。** 留存资本必须结算同笔恢复。ADR-0035 已修订；旧全体持有人 checkpoint 账本已删除，不保留两种模式。

实现采用原始准备金整数单位和现有 OZ EnumerableSet。激活只遍历最多 128 个活跃风险仓位；结算不遍历历史批次。全部退出时剩余虚拟/取整风险归协议，后续入金不取得无主旧权益。两级舍入尾差持续备付，直到对应全部单位的最终权益已分配。
