## 1. 已选择的模型

玩家按签名前确认的游戏规则承担投注风险，了解派彩扣减与独立交易成本；LP 因提供赔付资本获得规则化的费用留存；协议获得服务预算；推荐方从有限的已发生费用中获得奖励。玩家返现不作为首阶段必要条件，也不能在推荐预算之外另建未覆盖的支出。

首阶段采用实际费用分配，原因是它能把新增外部债务与本回合实际扣减对应起来。以使用流水估算的理论 edge 不再被直接全额计提为协议或推荐债务。

LP 的费用份额保留在 Bank 净资产，不另铸一份可以重复领取的奖励。它与游戏的实际盈亏共同进入份额价值。协议领取与推荐领取分别减少资产和已经建立的外部负债，不再次扣减 LP 收益。

## 2. 单位、预算和会计约束

所有链上计算使用相应资产的最小单位。下文 `H、p、x` 使用 bps 整数：`0 <= H <= 10000`，`p >= 0`，`x >= 0`，`0 < p+x < 10000`。其中 `H` 是玩家确认的派彩扣减率，`p、x` 是实际扣减中分配给协议、推荐方的最高比例；LP 的最低比例为 `0 < l = 10000-p-x < 10000`。是否允许零扣减的活动配置是独立活动政策，不能改变上述预算约束。

```text
S = 投入 stake
Q = 未参与回合的本金退款，0 <= Q <= S
U = S - Q，实际使用流水
G = 游戏模块给出的毛派彩
F = floor(G × H / 10000)，实际派彩扣减
N = G - F，玩家净派彩

P_cap = floor(F × p / 10000)
X_cap = floor(F × x / 10000)
P = P_cap，建立应付协议负债
X = 实际建立的全部推荐奖励负债，0 <= X <= X_cap
L = F - P - X，保留在 LP NAV

F = P + X + L
P + X <= F
L >= F - P_cap - X_cap >= F × l / 10000
ΔNAV = U - N - P - X = U - G + L
```

`L` 是本回合费用留存，不等于本回合 LP 盈利。玩家大额中奖时，即使 L 为正，`ΔNAV` 仍可为负。分析以上完整生命周期时，起点应在本回合 stake 入账前；不能把尚未结算的 stake 入账误当已实现经营利润。

令 `PF、XP` 为池内累计未领取的协议和奖励负债，`B` 为实际资产余额，`NAV=B-PF-XP`。新增 P、X 在结算时立即扣除 NAV；XP 的可领、待解锁、保留桶均计入负债。对外领取时，B 与对应负债同步减少，NAV 不再受同额影响。协议费用回补池内、直接捐赠、LP 存取和份额转移应另行归因。

### 2.1 毛赔付准备金同时覆盖新增外部债务

当模块已满足 `G+Q <= reserved`，选择的分配模型可推出：

```text
玩家净派彩 + 本金退款 + 新协议债务 + 新奖励债务
= N + Q + P + X
<= G + Q
<= reserved
```

因此分配不会在同一回合的毛派彩准备金之外，再增加一笔按流水估算的外部债务。预留必须覆盖全部允许的正常结算与异常退款路径；允许全额退回 S 时，开仓必须保证 `reserved>=S`，不能只验证正常游戏路径的 `G+Q<=reserved`。完整实现仍须验证并发头寸、现存负债、资产准入、转账失败和异常退款；不能把单笔等式误当全系统安全证明。

### 2.2 资金结算边界独立执行预算与 LP 下限

最终目标是在 Router／Bank 资金结算边界执行校验，不能仅依赖新 Hub 的自律。F 由本次 `G-N` 推导，且与接受投注时冻结的 H 所计算的 `floor(G×H/10000)` 一致；配置包含 H/p/x 及其不可改写的版本身份，不能在结算时重新选取可变的全局分配率。玩家接受的费率上限也属于开仓验证。

X 必须汇总本次所有 accrued、locked、holdback 等新增奖励负债。除 `P+X<=F` 外，资金边界还校验 `P<=P_cap`、`X<=X_cap`，由此保证 `L>=F-P_cap-X_cap>=F×l/10000`。例如 F=100、P=100、X=0 虽符合总预算，却会让 L=0；只有总预算检查不足以执行已经定义的 LP 最低份额。

这仍不让资金层知道真实开奖结果。它限制授权 Hub 提交的支付与费用在预留及已接受分配条款内；错误结果、错误毛派彩或错误的最大预留仍需要规则模块、随机数、准入和独立审查约束。

### 2.3 无推荐、舍入和资格的推荐落地规则

内部推荐如下，进入实现规格时应写为明确的状态转换，而不是依赖前端约定：

1. **没有有效推荐人：**`X=0`，X_cap 全部留在 L；协议仍仅获得 P_cap。不得沿用旧引擎“缺失推荐进入协议 sink”的默认语义。
2. **层级未填满或分配舍入：**只对真实存在且符合绑定规则的接收人建立负债，未分配金额留在 L；层级各项向下取整，所有层级、玩家 kickback（若以后引入）、保留与其他奖励总和不得超过 X_cap。首阶段推荐单层归因，扩展层级需证明额外获客价值。
3. **未达到可领取门槛：**如果奖励权利已成立，其金额仍完整计入 X，只是进入 locked/holdback，不能既当 LP 留存又承诺未来补发。是否取得奖励权利与何时可领取应分别定义。
4. **认定无效或反滥用：**应在建立债务前依据已快照、可验证的条件判定；已建立债务不得被运营方事后无声取消。若引入追索/失效条件，需要独立规则、证据、申诉与会计设计。
5. **纯退款：**未发生有效游戏结算时，`G=F=P=X=L=0`，游戏本金按规则退还；已支付的链上 gas 和已经消费的随机数费用不因此自动退还。

为降低报价复杂度，首阶段推荐方从统一基础费用中分成，**不增加未明示的渠道加价**。若后续有增量定价需求，应作为新版本的价格政策校准，并在同一 F 总预算内分配；必须给玩家展示最终扣减和上限。

## 4. LP 激励、价格与参数校准

### 4.1 使用流水收益率不是 LP 本金收益率

对于固定 U，令 `q=E[G]/U`，忽略资产和分配整数舍入，且存在有效推荐人、按完整比例分配，记 `h=H/10000`、`αP=p/10000`、`αX=x/10000`、`αL=1-αP-αX`：

```text
E[玩家净派彩] = (1-h)qU
E[LP NAV 贡献] = (1-q+αL hq)U
E[协议预算] = αP hqU
E[推荐预算] = αX hqU
```

无有效推荐时，αX 对应的费用留在 LP；这会提高该来源流水的 LP 期望，但不能在对所有流量的估算中同时假设“全部有推荐佣金”和“全部无推荐留存”。

若毛赔付公平 q=1，LP 的单位流水理论期望为 αLh；它要补偿赔付方差和尾部损失，并非存入资本的固定回报。不能在缺少实际资金周转、最大敞口、取款行为和流量证据时，用“单位流水期望 × 想象的周转次数”给出 APY。

批量停止使 U 成为随机量。精确校准应使用 `(U,G)` 联合分布并应用链上整数公式；不能把预先授权/投入的 S 当实际 U。有限独立同分布回合、停止仅依据过去结果等条件成立时，可证明 `E[G]=qE[U]` 并简化模型，但手续费取整仍在整笔聚合结果上计算，不能忽略这些适用条件。停止规则是按毛结果还是扣费后净结果也必须在报价中明确。

### 4.2 三个内部敏感性输入

为了比较分配比例的影响，先固定**仅作算术输入**的 `h=2%、q=1`，有有效推荐，忽略整数舍入与成本。以下不是已选择的上线比例，不可直接进入营销收益文案。

| 校准输入 | LP / 协议 / 推荐费用份额 | 每 1 USDC 实际流水的 LP 理论贡献 | 协议理论预算 | 推荐理论预算 |
| -------- | ------------------------ | -------------------------------: | -----------: | -----------: |
| S1       | 50% / 30% / 20%          |                       0.010 USDC |   0.006 USDC |   0.004 USDC |
| S2       | 60% / 25% / 15%          |                       0.012 USDC |   0.005 USDC |   0.003 USDC |
| S3       | 70% / 20% / 10%          |                       0.014 USDC |   0.004 USDC |   0.002 USDC |

**50/30/20 当前仅为算术示例，不是各参与方利益承诺。** 增加 LP 比例会减少协议和/或推荐预算，团队应通过服务成本覆盖和实际获客效率选择可行域，而不是向每一方分别许诺同一笔收入。

### 4.3 最小经济投注额评估

最小金额既是精度问题，也是费用是否合理的问题。评估应按网络、资产、玩法、回合数和当前费用报价进行，不能直接借用其他项目的最低下注额。

令 `C_user` 为每次请求玩家承担的独立成本，折算为下注资产，包含下注 gas、实际 VRF charged、必要授权成本的明确分摊，以及需要单列的恢复成本。使用报价汇率和时间戳，不假定原生资产与下注资产价格固定。令 `τ` 为团队通过体验研究确定的独立费用占使用金额上限：

```text
独立费用占比 = C_user / U
用户成本约束：U >= C_user / τ
```

若讨论的是含游戏期望损失的总成本上限 κ，则令 `e=1-(1-h)q`，且必须 `κ>e`，才有 `U >= C_user/(κ-e)`；该式是模型成本约束，不是指导用户增加下注。对于可在第一回合停止的批量请求，至少同时检查最小可能 U 与 E[U]，不能仅用计划最大 S 稀释费用占比。

令 `C_protocol,var` 为每请求协议实际承担的可变成本，`m` 为内部成本覆盖余量，则有推荐、比例足额分配的近似约束为：

```text
αP h q E[U] >= (1+m) × C_protocol,var
```

分母 αPhq 为零时不能用“提高最低金额”求解；须明确由其他资金支付服务。协议固定成本另按观察窗口核算：`ΣE[P] >= ΣC_protocol,var + C_protocol,fixed + 运行储备增量`，不能在没有已观测请求量时凭空摊薄固定成本。随机数费用由玩家转付提供方，不能再作为协议已经支付的成本重复扣一次。

由上述下限与资本允许的最高金额共同形成可行区间。**若最低经济金额高于可承受的风险上限，就不存在当前条件下的可用产品区间。** 应降低执行成本、选择合适的请求结构、明确有期限补贴，或暂不提供该路径；不通过提示用户加大投注来掩盖问题。数学门槛最终采用清楚的分层报价/最小额规则，并验证整数舍入与潜在绕过。

| LP 承诺资本、资金集中度、退出行为及风险容忍度      | 在明确场景下做同时最大赔付、连续损失、提款拥挤和暂停压力测试         | 上限、缓冲和资本激励是否匹配    |

校准输出应是带来源和适用范围的版本参数包：H/p/x、无推荐规则、最小金额、批量上限、单注/单池敞口和运行储备；包含可行域与否决情景。采用有限的有效实测数据，不把模型输入写成市场预测。参数可由团队在已选路线内形成建议版本，不把每个数值重新变成对用户的决策问卷。

## 5. v1.5 差距与真实迁移边界

本节描述已读取的实现，不定义目标上限。观察依据包括冻结源码 `ac0bb9e2f7295a944679be5e130c29c3253552b7` 的独立经济分析及本次读取的相同相关路径；并非本次重新核验链上配置。

### 5.1 当前预算和引擎需要改变

当前 [GameHub.finalize](../../src/core/GameHub.sol) 对 G 扣 F，但 PF/XP 按 U 的基础与加价 edge 形成。合法 DefaultReferralEngine 配置、levels>0 时，`P+X=floor(U×baseHE/10000)+floor(U×deltaHE/10000)`。降低 baseBudget 只是把更多预算放入 PF，不自动提高 LP 留存；改变 holdback 也不取消 XP 债务。

现 [DefaultReferralEngine](../../src/engines/referral/DefaultReferralEngine.sol) 把缺失上级和舍入回到 sink，再由 GameHub 计入 PF。目标必须让未分配金额回 L，并把外部分配总额限制在实际 F。需要明确新引擎的返回值（已分配奖励、未分配额等）及独立守恒校验，不能只改字段名称继续沿用旧 sink 路径。

### 5.2 不可变地址和原有权利

| 真实边界                                                                                                             | 对下一版本的含义                                                                                                                                                |
| -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GameHub 的 router、vrfHub、referralRegistry、referralEngine 为 immutable；已注册 gameId 不能覆盖模块                 | 经济逻辑需新 Hub 部署或其他明确的新版本方案，不能假定 setter 可替换现 Hub 的结算代码                                                                            |
| [ReferralRegistry](../../src/engines/referral/ReferralRegistry.sol) 的 binder 只能设置一次，首触绑定不可覆盖         | 新 Hub 不能直接获得旧 registry 的 bindFor 权限；需设计旧绑定读取/迁移、新绑定入口和唯一归因来源，不能悄悄重置旧推荐关系                                         |
| [Bank](../../src/core/Bank.sol) 的 settlementRouter 只能设置一次                                                     | 若保留既有 Bank，应通过其既有 Router 接入新的合格 Hub；若需要替换资金层或 Router，须新 Bank/池与用户明确迁移流程                                                |
| [SettlementRouter](../../src/core/SettlementRouter.sol) 把 ownerHub 固定到每个 position                              | 旧头寸仍由旧 Hub 结算/退款；不能把旧请求映射到新 Hub 并套用新经济参数                                                                                           |
| [PoolRegistry](../../src/core/PoolRegistry.sol) 新开仓检查 Hub 注册及按池许可；已持有头寸结算依据 Router 的 ownerHub | 可分别限制旧 Hub 新风险与保留其债务退出路径，必须用实际状态证明待结算请求处理完毕，不能直接删除旧 keeper                                                        |
| 现 Bank/Router 检查毛派彩与退款上界，但没有独立强制 `新PF+新XP<=F`                                                   | 只增加 Hub 校验不能达到本稿最终目标。下一版本采用新 Bank／Router／Hub，使资金边界独立校验费用来源、冻结配置、PF／全部 XP 上限和 LP 留存下限；旧组合保留债务处理 |
| adapter 的 VRFHub 回调地址可被治理改变，旧请求记录仍在原 VRFHub                                                      | 共享旧 VRFHub 与给新实例配置独立 adapter 是不同迁移方案；有旧请求时不得随意把共享 adapter 的回调地址改到新 VRFHub                                               |
| keeper 当前按 release 中单个 gameHub 读取、模拟和发送 finalize                                                       | 并行期需覆盖旧、新 Hub，索引/队列/凭证使用明确 chain、Hub、position 身份，不能切换配置后遗忘旧负债                                                              |

下一经济版本选择新的 Bank／Router／Hub 发布单元，复用既有设计与代码基础并加入必要的字段和校验。单换 Hub 的方案不作为最终实现路径；是否复用 VRF 等辅助组件由待结请求和回调归属验证决定。旧资金池的资产不由运维脚本强制迁走，LP 在清楚新条款后自行决定迁移。

已有 PF、XP、LP 份额与等待头寸不因新模型上线消失。不能将既有 XP 归零以制造新 NAV，也不能用事后改比例挪走旧奖励。新的承保资本进入新的池，必要的披露、旧池退出窗口和资金路径进入迁移设计与验收；不能由前端替换地址暗中决定。

新版本每笔投注需要冻结价格、分配配置 ID/hash、经济版本、推荐归因及影响已接受权利的规则。事件、终态凭证、SDK、ABI/release bundle 和索引要能区分旧流水分配与新 F 分配，并逐笔重建 P、X、L。不能仅通过最终 NAV 差值反推每方应得金额。

### 5.3 实现顺序与针对性验证

1. 完成参数校准模型和可行区间，定下新引擎返回语义、快照字段及缺失推荐规则。
2. 实现新 Hub/引擎及 Bank／Router 资金边界校验；证明费用来源与冻结配置一致、F/P/X/L 守恒、LP 留存下限、准备金覆盖、退款无游戏分成、各种精度不超预算。
3. 同步报价、用户费用、LP 经营指标和推荐对账，显示派彩扣减、独立原生资产费用与领取状态。
4. 冻结部署与迁移方案，逐项验证旧头寸、旧推荐关系、旧 PF/XP、共享回调及 keeper 并行运行。
5. 经独立审核、部署模拟及限定环境业务验收后再发布参数包；实际资金和生产变更按具体发布操作执行，本文件本身不执行这些操作。

## 6. 替代方案的内部比较记录

为保持对外主册清楚，替代方案和否决原因保留在此，不将公开商业白皮书写成尚未选择的方案会议。

| 方案                            | 机制与理想期望                                                              | 本阶段处置                                                                                                       |
| ------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| A：流水预算预留 LP              | 先按 hU 留给 LP 一部分，再计外部债务；`E[ΔNAV]=[(1-h)(1-q)+αLh]U`，忽略舍入 | 未选择。佣金可按流水预测，但玩家本局无赔付、F=0 时也计外部债务；需额外覆盖路径风险，不具备选择模型的逐笔实收上界 |
| 已选择的实际 F 分配（此前称 B） | `E[ΔNAV]=[1-q+αLhq]U`，外部债务不超过 F                                     | 下一 casino 经济版本的实施路线。推荐收入随派彩波动，需用真实渠道与运行数据校准                                   |
| C：周期已实现利润/高水位        | 结转历史损失、补足准备金，再分配可用利润                                    | 后续研究。需要份额高水位、存取款归因、跨期奖励和退出时间规则；不把简单 NAV 差或 GGR 当可分配利润                 |

公平毛赔付 q=1 时，A 与选择模型均可得到 αLhU 的 LP 理论期望，区别在实际资金路径和方差。不能仅凭相同期望忽略偿付与推荐收入波动。

手动把协议 PF 回补 Bank 是当前代码可研究的治理路径，独立测试已验证标准 MockERC20 的 self-transfer 会令 B 不变、PF 减少、NAV 增加；这不是自动 LP 分润，不适合作为目标默认机制，也不代表生产资产路径已验证。
