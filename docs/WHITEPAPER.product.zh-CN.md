## 摘要

ArbiGameFi 是以钱包访问、链上游戏规则与逐笔结算凭证为核心的 casino 项目。v1.5 包含八款游戏，部署于 Base 与 Base Sepolia。当前适合招募测试网体验与反馈；主网虽完成指定小额验收，网站主网投注仍未开放。Sportsbook 的源码存在，但未纳入当前部署。

产品价值在于用户能在签名前检查参数与费用，在完成后核对结果与资金去向。它仍依赖智能合约、治理、资产、网络、随机数与应用服务，不能用“无需信任”概括掉这些边界。

## Abstract (EN)

ArbiGameFi is a wallet-accessible casino project with on-chain rules and inspectable settlement receipts. Its v1.5 release includes eight games on Base and Base Sepolia. Testnet feedback is the present public-use focus; mainnet single-round acceptance has been completed, but the website has not enabled public mainnet betting. Sportsbook remains outside the deployed release. Player payouts, protocol/referral revenue, and LP net asset value follow different accounting rules. The current mechanism must not be marketed as guaranteed or inherently positive LP yield.

## 2. 玩家体验：先理解，再签名

正常路径是：

```mermaid
flowchart LR
  A[选择网络与游戏] --> B[准备 USDC 与 ETH]
  B --> C[核对金额、规则、净派彩和费用]
  C --> D[必要时授权 Bank]
  D --> E[签署投注]
  E --> F[等待随机数与结算]
  F --> G[核对结果和交易凭证]
```

- 测试网资产无真实价值，应使用对应网络的测试 ETH 与测试 USDC，不能混用主网余额。
- ETH 用于钱包交易 gas 和 VRF 请求费用；两者不同。失败交易也可能消耗 gas。
- 首次或额度不足时，授权和投注是两个独立步骤。授权成功不表示已下注；已有足够额度可以跳过授权。
- 投注资金进入 Bank 智能合约，结算或退款回到记录的玩家钱包。平台不保管私钥，不要求预充值平台账户，但不能声称资金始终留在钱包。
- 钱包拒签、切错网络、池暂停、余额不足、报价变化与 RPC 延迟应分别说明原因。提交结果未知时先查钱包和哈希，再决定是否操作。
- 随机数与结算有等待时间。满足状态条件时可手工触发结算或申请退款；不能承诺任意时刻取消投注。

手机端支持钱包内置浏览器及钱包连接流程；实际跳转取决于操作系统、安装的钱包与连接方式。普通网页不能可靠枚举用户安装的所有钱包，不能承诺自动检测或所有设备无缝跳转。

## 3. 透明性应体现为证据

| 用户疑问     | 可核对内容                             | 边界                                           |
| ------------ | -------------------------------------- | ---------------------------------------------- |
| 结果来自哪里 | VRF 请求、随机数哈希与回调事件         | 不等于所有赔率或页面显示都经过认证             |
| 钱去了哪里   | 玩家转账、Bank 账本、最终派彩/退款交易 | 索引或网页显示可能延迟                         |
| 能赔付多少   | 该池净资产、预留、当前最大投注与报价   | 不应以全站总资产保证某一池任意赔付             |
| 谁能改规则   | 治理、guardian 和具体可修改参数        | 2/3 Safe 不证明由三家独立机构管理              |
| 出问题怎么办 | 状态页、收据、条件退款、运维与披露入口 | 网站故障不触发自动退款，也不是固定时间退出保证 |

已有源代码、金库、凭证和状态页应形成连贯入口。下一步是对齐这些内容及易读说明，不靠虚构用户数量、成交额、收益或审计徽章建立信任。

## 4. 经济机制：玩家、协议、推荐与 LP 分开说明

### 4.1 玩家支出

玩家承担投注结果、按净派彩规则体现的费用、VRF 原生币请求费与钱包交易 gas。各游戏的赔率、胜率与整数取整不同，不能统一宣传固定回报率。“庄家优势”不等于用户每局必然损失固定比例。

### 4.2 协议和推荐奖励

GameHub 按实际使用流水与 edge 计算基础/增量预算，未分配部分可形成协议应付费 PF，推荐奖励形成 XP。PF/XP 会从 LP 净资产中扣除。XP 可能需要来源玩家流水达标、保留期成熟和资金池允许出金，不能把“产生奖励”写成“立即收到现金”。

当前冻结参数的含义见[事实表](release/STATUS-v1.5.zh-CN.md)：不把引擎支持的多级或增量机制宣传成已运行政策，不把计划中的玩家奖励当作现有返现权益。分享链接、本地首次来源记录、链上绑定与实际奖励分别核对。

### 4.3 LP 持有什么、承担什么

LP 将资产存入一个 Bank，获得随该池 NAV 变化的份额。LP 承担玩家盈亏的结果方差、合约及治理风险、资产风险和流动性约束。提现取决于当前可提现额度、准备金、出金缓冲与暂停状态，并非随时全额兑现。

```text
NAV = Bank 资产余额 - 协议应付费 - 推荐等外部负债
单笔净值变化 = 已使用流水 - 玩家净派彩 - 新增 PF - 新增 XP
```

上述单笔净值变化从该投注接受前计算到结算后，排除同期 LP 流入流出、捐赠及资产外部变化。

“流水减毛派彩”是 GGR，不是 LP 净收益。现有实现不能直接支持“LP 获得庄家优势，因此稳定盈利”的说法。

以公平二选一 Coin Toss、1 USDC、2% edge、总 PF+XP=0.02 USDC 为例，赢局 LP 净变化 -0.98，输局 +0.98；等概率理想模型中期望为零，仍有波动。示例不包含其他现金流、gas、取整影响或对全部模块的收益推断。详细推导见[技术白皮书第 6 节](WHITEPAPER.zh-CN.md#6-费用协议收入与-lp-经济)。

**LP 激励是否可持续，是进一步业务与经济评估事项。** 在明确 LP 补偿来源、验证各游戏分布与费用分配之前，不采用“做庄稳定收益”、理论高年化或固定 APY 吸引资金；文档修改不等于已改变协议分配。

## 6. 推广前的产品优先级

### 已有基础

八款游戏与回执、LP 操作、推荐入口、五种 UI 语言、FAQ、状态页、基础 SEO/分享图、钱包连接与错误分类已存在。白皮书正文当前为中文附英文摘要，不能把 UI 多语言等同完整多语言资料。

### 本轮之后应完成

1. 对齐首页、页脚、帮助与游戏入口的网络和开放范围；未部署 sportsbook 不作为现售功能。
2. 完善首次体验说明，分别显示授权、投注、随机数和结算；保留不确定交易的防重复保护。
3. 修正 LP 指标语义，验证所有收益和赔付展示，明确责任游戏设置的实际执行范围。
4. 使推广链接保留目标网络与来源信息，并验收真实 iOS/Android 钱包跳转。
5. 用现有 Markdown 建立站内阅读入口，先发布中英文项目简介、入门、费用、风险与核验指南。
6. 在尊重同意设置的前提下补齐漏斗测量；当前只有 analytics 基础，尚无完整业务事件链。

当前浏览器本地自我排除不是跨设备或链上限制，每日存款/亏损设置尚无交易路径强制执行证据。它们不能在宣传中被描述为已实现的完整限额体系。
