> 读者：项目负责人、内容作者、商业与技术审阅者

## 1. 先明确读者的决定

每份材料开始写作前，先确定一个首要读者群、一项读后决策和支撑该决策的证据。项目生态中存在玩家、LP、推广和运营角色，不意味着每份白皮书都应该逐个向他们说明全部产品。

[项目总纲](strategy/project-master-plan.zh-CN.md)组织定位、商业命题、建设选择与资源安排；对外材料据此表达各自读者需要的项目逻辑。代码和运行记录验证具体能力，用户研究验证市场假设。对外白皮书同时可以阐明未来愿景与设计，但不承担内部方案讨论会或研发工单职责。

## 3. 每份白皮书怎样组织

商业主册以读者的资源决策为主线：项目命题、目标市场与客户、替代选择与差异、产品组合、收入与成本、资本需求、分发与留存、执行能力、路线及关键风险。用户旅程只在解释价值时简述，完整页面需求留在 PRD。

技术白皮书以机制论证为主线：设计问题与目标、选择依据、参与者与资金模型、状态与权利、约束、结果与结算、安全假设、治理、演进及验证入口。数学式要定义单位、范围、舍入和适用条件；审计发现和发布日志单独链接。

简介为初次阅读而写，可独立理解，并把读者送到适合他的下一步。它不是从技术白皮书各节各摘一句，也不重复整套内部经济选项。

[内部经济设计](strategy/economic-design.md)保留候选比较和校准情景；对外说明已经选择的设计方向及其适用版本。未完成实现的方向集中说明，不逐段堆叠“待决”代替观点。

## 4. 主张和证据的规则

- **战略选择**说明我们选谁、做什么及为什么；其依据和取舍归入总纲。
- **市场假设**明确仍需验证；不得写成访谈结果、客户承诺或已证实的留存。
- **外部观察**引用官方原始材料并注明查阅日期；从个别产品推断整体市场时必须收窄结论。
- **当前能力**链接带日期、版本和适用范围的事实，不混用代码存在、已部署、已开放和已验收。
- **目标机制**标明目标版本或设计状态；项目负责人可以确定规划方向，公开条款则需要相应实现和发布证据。
- **经济示例**定义分母、单位和假设，写明是演算；真实经营数据另附时间、口径与证据。

不编造市场规模、份额、营收、TVL、客户、合作关系、团队履历或牌照。不把链上可验证、源码验证、多签和第三方审计混为同一保证。明确随机数可信度、支付偿付、治理和资产风险的不同边界。

市场资料不足时，缩小论证范围并安排研究；不以空泛“巨大市场”“行业领先”填补。竞争材料用来确定要证明的差异，不转抄竞品的营销自评。

## 5. 编辑与语言

三份对外主稿沿用 `AGF-WP-BIZ / AGF-WP-TECH / AGF-BRIEF-YYYY.MM-rN`，标明日期、首要读者、语言和审阅／发布状态。原文件路径保持兼容，标题可按真实职责调整。

内部草稿、外部审阅稿和正式发布稿是编辑状态；目标版本、现行版本是机制适用范围，不能相互替代。将内容合入 Git 只表示保存了这份材料，不自动开启网站业务或产生新的资金权益。

首轮提供完整中英项目简介，长版先形成统一中文内容与英文摘要。长版英文和站内版应基于通过审阅的同一逻辑翻译，不写两套承诺。语言不等于服务地域。页面截图、测试演示与真实交易凭证标明身份。

## 6. 按受众进行验收

商业审阅者应能回答：谁是首批客户、为什么会选择、钱怎么流、成本如何覆盖、增长如何发生、合作有什么意义、哪些事实还没有证据。

技术审阅者应能回答：资金与权限归谁、规则如何冻结、输出如何验证、最坏责任怎样约束、外部依赖失败会怎样、如何核对实际实现。

首次阅读者应能复述项目定位并找到与自己相关的下一步。若三份材料都只让人记住同一组公式、阶段编号和待办，视为分工失败。

最后再检查链接、格式、术语、示例算术、图示和跨文档一致性。这些检查只证明编辑完整性，不能替代受众测试、商业验证或工程审查。实际发布时记录版本与渠道；历史运行证据保持原日期与范围。
