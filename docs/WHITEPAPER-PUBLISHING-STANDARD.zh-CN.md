## 1. 白皮书的定位

白皮书是项目的设计指南。它应说明 ArbiGameFi 要为谁解决什么问题、选择怎样的产品与机制、为什么这样设计，以及如何分阶段实现。代码、测试和链上状态用于检验实现是否符合设计，并揭示需要修订的假设；它们不代替产品目标，也不限定白皮书只能描述已有功能。

产品定位遵循 [Fullstack Product Architecture Commitment](strategy/fullstack-product-architecture.md)：以协议级结算内核支撑单品牌 B2C casino/sportsbook 产品，服务玩家、LP、推广伙伴及本项目运营。白标和第三方运营基础设施属于有真实需求后再评估的方向。产品定位、目标范围与某次发布已开放的范围分别表达。

白皮书可以提出尚未实现的经济与治理方案，但必须标明“设计草案”或“待决方案”，解释动机、约束、取舍与验证方式。未有明确决策依据，不写成已批准；未有发布证据，不写成已部署、已开放或已验收。

## 3. 正文应如何展开

产品白皮书应从目标用户与问题出发，说明愿景、产品范围、用户路径、价值交换、经济设计和发展路线。技术白皮书应从设计目标与约束出发，说明组件职责、资金与控制流、生命周期、关键不变量、外部依赖和演进方式。简介提炼两者，路线图承接两者。

每个重要方案应讲清：

1. **目标与原则**：为什么需要它，要改善谁的体验或保护什么边界。
2. **机制与取舍**：参与者、输入、状态变化、价值或资金流，以及选择它的原因。
3. **设计状态**：已有决策依据、仍待比较的选项，以及尚未验证的假设。
4. **实施路径**：依赖、阶段交付物和判断方案成立的条件。

实现与设计存在差距时，用简短说明和事实表链接标出差距。不要为了贴合已有代码而删去必要的目标设计，也不要把预期机制写成现有产品承诺。

## 4. 设计状态与实施状态

三类状态分别标注，不相互替代：

- **设计状态**：“设计草案”表示可讨论的提案；“待决方案”表示仍有选项需要选择；已有明确决定的方案应引用对应决策记录及其范围。文档作者不得自行赋予批准状态。
- **编辑与发布状态**：`Review Copy` 是审阅稿；`Release Candidate` 是准备发布的稿件；`Published` 仅在实际发布并记录固定版本与渠道后使用。以上状态均不代表方案获批或功能上线。
- **实施状态**：实现、部署、开放、验收分别记录于发布事实表。指定提交有代码不等于网络上已部署；已部署不等于网站已开放；已开放不等于所有场景已验收。

经济或治理设计草案应说明价值来源、参与者权利义务、分配依据、参数边界、管理与变更权限，以及需要验证的风险。比率写明分母和适用条件；方案示例不称收益预测。代币、分成、投票权、时间锁或 Safe 设计未被明确采纳时，不写成项目承诺。

## 5. 元数据与表述

每份白皮书、简介与路线图至少标明项目、文档编号或修订号、日期、语言、目标读者、编辑状态和关联设计文档。涉及实施现状的章节链接带日期的发布事实表；引用具体实现或测试结论时，才附对应提交或发布基线。设计稿不必随每次代码提交重新定义自身版本。

编号沿用 `AGF-WP-TECH / AGF-WP-BIZ / AGF-BRIEF / AGF-WP-SYSTEM-YYYY.MM-rN`。协议版本、文档修订号、路线图阶段是不同标识。

- 项目品牌统一为 ArbiGameFi；SSOT 表示 Single Source of Truth 架构原则。
- 分开解释毛派彩、净派彩、GGR、PF、XP 和 LP NAV；新经济机制说明它与这些量的关系。
- “非托管”应交代用户私钥、钱包授权与进入合约后的资产保管边界。
- permissionless 应说明状态条件、交易要求及治理可变参数。
- Safe 阈值不等同于多机构治理、时间锁或绝对安全。
- 源码验证、自动测试、内部审查、第三方审计与形式化证明分别命名。不同 Codex 工作单元的审阅不称第三方机构审计。
- 不作“永不卡款”“保证本金”“固定高年化”“资金始终在钱包”等无条件承诺；浏览器本地提醒不写成跨设备或链上强制控制。

## 6. 修订与审阅流程

1. 先确认目标用户、产品定位、设计原则与本次需要解决的设计问题。
2. 更新受影响的产品或技术方案，明确选择、待决项及其理由；同步路线图中的依赖、阶段与判断条件。
3. 检查与既有设计决定的一致性。若需要改变既有决定，明确提出变更及影响，不通过改写白皮书隐含宣告批准。
4. 核对文中关于现状的陈述。需要新的实施结论时，在相应范围核对源码、测试或发布证据并更新事实表；不把每次编辑变成一轮系统审计。
5. 审阅逻辑、公式、参与者权利、权限边界、可理解性及产品/技术/简介/路线图之间的一致性；必要的实现验证由对应工程任务完成。
6. 检查本地链接、术语、图示、英文摘要和元数据，记录修订范围。实际发布后再更新发布状态。

设计修订记录解释“目标或方案为何改变”；实施复盘记录解释“实现或运行中发生了什么”。两者互相引用，但各自保持用途。

## 7. 多语言、图示与分发

中文为当前正文，长版保留英文摘要，简介保留英文快速说明。后续英文版、站内 HTML 与 PDF 从同一设计内容维护，明确语言和修订版本，避免另造产品承诺。

产品图解释用户任务、价值交换与阶段演进；技术图解释组件责任、资金流、控制权和状态转换。尚未采纳的方案标注设计草案，目标架构与已部署架构分别标注。实际游戏展示、统计和示意图分开说明；测试网资金不得合并为真实 TVL。

过往版本由 Git 保留。历史规范、签名域与验收证据保留原版本，不做全局协议版本替换。设计方向变化不改写历史发生过的事实；旧运维指南是否仍适用由发布入口说明。
