## 2. 四种事实必须分别核实

1. **实现**：指定提交中有代码与测试。
2. **部署**：指定网络、地址、代码与治理对应已验证 release。
3. **开放**：网站开关、合约暂停、池和资产条件允许使用。
4. **验收**：指定场景有实际测试或交易证据。

不能从任意一项自动推出其余三项。历史进展日志不作为今日状态摘要；动态内容集中维护在事实表。

## 3. 元数据与状态

每份外发资料至少标明项目、文档编号、状态、日期、语言、读者、发布基线、代码提交和关联文档。协议版本、文档修订号、里程碑编号是不同标识。

编号沿用 `AGF-WP-TECH / AGF-WP-BIZ / AGF-BRIEF / AGF-WP-SYSTEM-YYYY.MM-rN`。

- `Review Copy`：可审阅草稿，不等于对外正式发布。
- `Release Candidate`：事实与编辑检查通过，等待实际发布。
- `Published`：已完成发布并记录固定版本与渠道。
- `Working Standard`：维护规范。

本轮三份资料为 Review Copy。独立核查由不同 Codex 工作单元执行，不应宣传为独立第三方机构审计。修改文档不改变生产配置或链上状态。

## 4. 经济与信任用词

- 分开解释毛派彩、净派彩、GGR、PF、XP 和 LP NAV。
- 比率同时写明分母、适用模块和配置；示例注明条件，不称收益预测。
- “非托管”需解释为不保管用户私钥、不要求预充值平台账户；资产进入合约后的保管事实不能隐藏。
- permissionless 必须同时说明状态条件、必要交易与治理可变参数。
- 治理 Safe 阈值不是多机构治理、时间锁或绝对安全的证明。
- 源码验证、自动测试、内部审查、第三方审计、形式化证明分别命名。
- 不使用“永不卡款”“保证本金”“固定高年化”“资金始终在钱包”等无条件承诺。
- 浏览器本地提醒或限额设置不能写成跨设备/链上强制风控。

## 5. 修订与审阅流程

1. 冻结 commit/tree，记录当前工作区与受影响发布。
2. 从源码、测试、发布制品和限定范围的链读核对事实，保留失败与遗漏。
3. 先修事实表，再改技术、产品、简介；只保留必要重复。
4. 由未参与执笔的审阅者检查公式、权限、边界、英文摘要与来源。
5. 检查本地链接、过期路由/文件名、术语和元数据；格式通过不能替代内容核验。
6. 记录修订范围、验证结果与未完成工作。只有实际完成发布后才标记 Published。

文档变更通常不需要重跑全部产品测试；系统复盘所运行的测试应写清命令、输入范围和 skip，不反复运行已通过套件以扩大“绿”的数量。

中文为当前正文，长版保留英文摘要，简介保留英文快速说明。后续完整英文版与站内 HTML/PDF 从同一 Markdown 内容维护，明确语言版本，不制造第二份事实源。
