## 1. Purpose

This document defines the intended visual direction for ArbiGameFi before high-fidelity screens are produced.

It exists to stop the product from drifting between:

- protocol dashboard visuals
- generic crypto gradients
- generic casino cloning

The direction board is not the final design system.
It is the agreed visual thesis the final design system must follow.

---

## 2. Brand Thesis

ArbiGameFi should look like:

- a premium on-chain gaming product
- with institutional trust rails
- and a room-first gameplay experience

It should not look like:

- a DeFi admin panel with purple gradients
- a generic casino skin with loud neon noise
- a speculative web3 landing page disconnected from the actual product

Working brand sentence:

> ArbiGameFi is where premium game-room energy meets transparent, auditable on-chain settlement.

---

## 3. Visual Positioning

The visual system should sit at the intersection of three aesthetics:

1. premium game-room atmosphere
2. modern financial clarity
3. web product discipline

This means:

- rich backgrounds, but controlled
- strong contrast, but not visual chaos
- dramatic room surfaces, but precise controls
- trustworthy information design, not dashboard sprawl

---

## 4. Reference Directions

These are directional references, not cloning instructions.

### 4.1 Zeebit

Borrow:

- room rhythm
- first-fold dominance of the game table
- compact bet slip
- clear distinction between play surface and surrounding chrome

Do not borrow:

- exact branding
- exact colors
- generic “web2 casino” polish without protocol trust expression

### 4.2 Institutional Fintech / Capital Interfaces

Borrow:

- clean metrics hierarchy
- disciplined table layout
- restrained confidence signals

Use this mainly for:

- liquidity
- account
- bets
- claims

### 4.3 Editorial Web Product Landings

Borrow:

- stronger hero hierarchy
- cleaner section pacing
- fewer but stronger proof points

Use this mainly for:

- home
- games directory

---

## 5. Experience Keywords

The final UI should feel:

- sharp
- premium
- controlled
- trustworthy
- immersive
- intentional

The final UI should not feel:

- busy
- improvised
- component-driven
- toy-like
- over-glowing
- over-explained

## 6. Route-by-Route Tone Mapping

## 6.1 Home

Tone:
- editorial
- persuasive
- premium

Hierarchy:
- headline first
- trust second
- live proof third

Visual attitude:
- broader spacing
- larger typography
- fewer cards
- more atmosphere

## 6.2 Games Directory

Tone:
- selection-driven
- comparative
- fast-scan

Hierarchy:
- room grouping first
- featured room second
- room cards third

Visual attitude:
- cleaner than a room
- more structured than landing

## 6.3 Game Rooms

Tone:
- active
- focused
- table-first

Hierarchy:
- game selector
- room identity
- play surface
- bet slip

Visual attitude:
- strongest contrast
- strongest game-specific expression
- minimal top chrome

## 6.4 Trust / Audit Routes

Tone:
- precise
- calm
- factual

Hierarchy:
- summary first
- explanation second
- raw detail third

Visual attitude:
- less cinematic
- more structured
- more neutral backgrounds

## 7. Color Direction

The current product leans too heavily on undifferentiated violet surfaces.
The new direction should use a broader but disciplined palette.

## 7.1 Core Palette Roles

### Background

- deep navy
- graphite blue
- dark indigo-black

Purpose:
- create depth without flattening everything into one purple field

### Energy Accent

- magenta-violet
- electric cobalt

Purpose:
- active room emphasis
- CTA focus
- selected state

### Trust Accent

- emerald
- teal

Purpose:
- success
- solvency
- safe action / confirmed state

### Warning / Risk

- amber
- restrained red

Purpose:
- pending
- refund delay
- failed action
- constraint surfaces

## 7.3 Color Use Rule

The UI must not use color as decoration only.

Color should indicate:

- primary action
- selected state
- bet family emphasis
- trust status
- warning or failure

## 8. Typography Direction

Typography should separate the three product modes.

## 8.1 Recommended Pairing Direction

Primary display:
- `Space Grotesk` or equivalent geometric grotesk

Secondary / UI body:
- `Sora`, `Manrope`, or equivalent clean sans

## 8.2 Typography Rules

Landing:
- larger, more expressive headlines
- shorter supporting copy

Gameplay:
- compact, high-contrast labels
- bold numeric emphasis

Trust routes:
- tighter data typography
- consistent table numerics

## 8.3 Numeric Treatment

Numbers matter heavily in this product.

Therefore:

- balances
- stake
- payout
- counts
- percentages

must use highly legible numeric styling and consistent alignment.

---

## 9. Surface System

## 9.1 Home Surfaces

- large atmospheric sections
- fewer borders
- stronger depth through background and spacing

## 9.2 Room Surfaces

- one dominant play canvas
- one secondary bet slip
- all other surfaces subordinate

## 9.3 Trust Surfaces

- flatter and calmer
- clearer groupings
- table and metric cards prioritized

## 9.4 Surface Rule

If every region is a bordered rounded card, hierarchy is lost.

The design system should deliberately mix:

- full-width sections
- embedded panels
- table surfaces
- lightweight info strips

---

## 10. Component Expression

## 10.1 Buttons

Primary CTA:
- strong fill
- high contrast
- route-specific emphasis

Secondary CTA:
- quieter
- less glow

Danger / risk CTA:
- explicit color change

## 10.2 Pills / Chips

Use for:

- room selector
- status
- active bet family
- quick stake actions

These should feel crisp and tactile, not ornamental.

## 10.3 Cards

Cards should have distinct roles:

- hero card
- metric card
- bet slip card
- trust card
- table card

One generic card style for all use cases is not acceptable.

## 10.4 Tables

Tables must favor:

- spacing discipline
- row clarity
- action discoverability

They should read like audit tools, not dashboard leftovers.

---

## 11. Motion Direction

Motion should be restrained and purposeful.

Use motion for:

- page entry
- room selector changes
- active bet confirmation
- transaction state changes

Avoid:

- decorative constant pulsing
- casino-style flashing overload
- repeated glow animations with no informational value

---

## 12. Iconography and Illustration

Icons should be:

- minimal
- clean
- not too playful

Game icons can carry more personality, but the system should still feel mature.

Illustration use should be limited to:

- landing hero accents
- room atmosphere support

It should not overpower product clarity.

---

## 13. Route-Specific Visual Rules

## 13.1 Home

Must feel:
- like a product destination page

Must not feel:
- like a control panel

## 13.2 Games Directory

Must feel:
- like a curated room directory

Must not feel:
- like a release manifest visualizer

## 13.3 Roulette Room

Must feel:
- like a standard European roulette table with a digital bet slip

Must not feel:
- like a params encoder
- like a grid of unrelated cards

## 13.4 Liquidity

Must feel:
- like an LP capital dashboard

Must not feel:
- like raw protocol accounting output

## 13.5 Bets

Must feel:
- like a ledger

Must not feel:
- like an indexer debug table

---

## 14. Explicit Do / Avoid List

### Do

- create one strong focal point per screen
- use different visual grammar per route family
- let game rooms feel like rooms
- let trust pages feel like financial tools
- use gradients sparingly but intentionally

### Avoid

- repeating the same card shell across every route
- overusing purple as the only visual lever
- exposing protocol terminology in the first fold of gameplay routes
- leading with diagnostics on conversion routes
- treating all routes as equal navigation peers
