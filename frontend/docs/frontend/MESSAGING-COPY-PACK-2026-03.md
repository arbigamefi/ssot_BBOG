## 1. Purpose

This document defines the public messaging baseline for ArbiGameFi.

It exists so that:

- the landing page does not invent value propositions route by route
- game rooms do not drift into generic casino language
- trust routes stay clear without sounding like internal protocol docs

This is the copy system that should be used before final screen design and before implementation.

---

## 2. Messaging Spine

### 2.1 One-line product definition

ArbiGameFi is a wallet-native on-chain game room product with auditable settlement.

### 2.2 Short positioning statement

Play premium on-chain game rooms with transparent settlement, readable risk surfaces, and no hidden custody flow.

### 2.3 Expanded product paragraph

ArbiGameFi combines active game-room play with protocol-grade trust rails. Players choose a room, place a ticket from their wallet, and follow each outcome through visible settlement paths. Liquidity, balances, and liabilities are presented as readable product surfaces rather than hidden backend mechanics.

---

## 3. Core Message Hierarchy

Every top-level marketing or product surface should reinforce the same hierarchy:

1. game rooms first
2. wallet-native flow second
3. auditable settlement third

This order matters.

Do not lead with:

- `single source of truth`
- `release artifact`
- `indexer`
- `infrastructure`

Those belong deeper in trust routes and documentation.

---

## 4. Message Pillars

### 4.1 Pillar A — Playable rooms

Headline idea:

`Step into live on-chain game rooms.`

Support message:

Users should immediately understand that this is a place to play specific rooms, not browse a research dashboard.

### 4.2 Pillar B — Wallet-native flow

Headline idea:

`Your ticket starts in your wallet.`

Support message:

Emphasize signature-based actions and the absence of hidden custody language.

### 4.3 Pillar C — Visible trust

Headline idea:

`Settlement stays readable.`

Support message:

Emphasize that bets, balances, fees, and liabilities can be inspected without turning the first screen into a technical document.

## 5. Public Copy Rules

### 5.1 Tone

Use:

- short sentences
- direct verbs
- product language
- calm confidence

Avoid:

- shouting casino language
- pseudo-institutional filler
- excessive web3 buzzwords
- unexplained abbreviations

### 5.2 Vocabulary rules

Prefer:

- `room`
- `ticket`
- `stake`
- `settlement`
- `wallet`
- `liquidity`
- `balance`
- `claim`

Use carefully:

- `bet`
- `protocol`
- `audit`
- `ledger`

Avoid on first-contact surfaces:

- `SSOT`
- `reconcile`
- `artifact`
- `indexer lag`
- `raw mask`

### 5.3 CTA rule

Every route gets one dominant CTA.

Avoid pairs like:

- `Play / Learn / Inspect` with equal weight
- `Start / Explore / Audit` all equally loud

## 7. Route-by-Route Copy Baseline

## 7.1 Home

Job:

- explain quickly
- build trust quickly
- route users into rooms quickly

Copy rules:

- lead with product promise
- keep proof points short
- avoid dense numeric surfaces

Suggested section labels:

- `Featured Rooms`
- `How it works`
- `Why trust it`
- `Live proof`

## 7.2 Games Directory

Job:

- help the user choose a room fast

Copy rules:

- compare rooms, not protocol mechanics
- use short descriptors
- keep each card scannable in 3 seconds

Suggested card fields:

- room name
- one-line style description
- one short fact row
- one CTA

## 7.3 Shared Game Room

Job:

- move the user from selection to ticket to confirmation

Copy rules:

- the room headline should be short
- supporting copy should not compete with the play surface
- left and right panels should read as action surfaces, not documentation

Suggested labels:

- `Manual`
- `Auto` only when implemented
- `Bet amount`
- `Number of bets`
- `Ticket summary`
- `Review ticket`
- `Place ticket`

## 7.4 Roulette Room

Job:

- make the table feel instantly legible

Copy rules:

- use standard European roulette language
- no legacy bitmask language in the main flow
- explain structured bets with short, plain labels

Suggested labels:

- `European roulette`
- `Main table`
- `Layout bets`
- `Straight`
- `Split`
- `Street`
- `Corner`
- `Six line`
- `Advanced raw bitmask` only in collapsed advanced mode

## 7.5 Bets

Job:

- provide a readable ledger

Copy rules:

- use factual labels
- do not dramatize outcomes
- prioritize status clarity over marketing tone

Suggested labels:

- `Recent bets`
- `Open ledger`
- `Status`
- `Updated`
- `Settlement`

## 7.6 Liquidity

Job:

- explain capital position and actions clearly

Copy rules:

- explain `NAV`, `reserved`, `buffer floor`, and `exit room` in product language
- present liabilities without defensive wording

Suggested section labels:

- `Capital summary`
- `What backs LP value`
- `What stays reserved`
- `Deposit liquidity`
- `Redeem shares`

## 7.7 Account

Job:

- help the user inspect balances and permissions

Suggested labels:

- `Wallet balance`
- `Bank shares`
- `Assets equivalent`
- `Allowance`
- `Refund credit`
- `Transaction journal`

## 8. Trust Copy Baseline

### 8.1 Short trust bullets

Use:

- `Wallet-native actions`
- `Readable settlement path`
- `Auditable room activity`

Avoid:

- `Trustless and decentralized forever`
- `Provably fair` as a standalone unsupported claim

### 8.2 Acceptable trust language

Good:

- `auditable`
- `readable`
- `transparent`
- `wallet-native`
- `visible settlement`

Use carefully:

- `non-custodial`
- `on-chain`
- `verifiable`

These should only appear where the product surface actually supports the claim and where context makes them meaningful.

## 10. Microcopy Patterns

### 10.1 Wallet disconnected

Use:

- `Connect wallet`
- `Connect wallet to review the live quote.`
- `Connect wallet to load your balance.`

Avoid:

- `Please connect your wallet first to continue this action`

### 10.2 Pending transaction

Use:

- `Waiting for signature`
- `Submitting ticket`
- `Waiting for confirmation`
- `Settlement still syncing`

### 10.3 Empty states

Use:

- `No indexed bets yet.`
- `No tickets found for this filter.`
- `No claimable balance right now.`

### 10.4 Explanatory helper text

Keep helper text:

- under two lines where possible
- near the action origin
- concrete about what changes

---

## 11. Banned Or Restricted Phrases

Do not use these as default public-facing homepage or room copy:

- `SSOT v2`
- `raw bitmask` outside advanced mode
- `release digest` in hero copy
- `institutional-grade` everywhere
- `provably fair` unless the exact support surface is clear
- `decentralized casino` as the main category line

## 13. Immediate Freeze Decisions

1. Public brand language leads with `ArbiGameFi`, never `SSOT`.
2. The default product one-liner is:
   - `ArbiGameFi is a wallet-native on-chain game room product with auditable settlement.`
3. The home hero should lead with playable rooms, not technical architecture.
4. Game rooms should use `ticket`, `stake`, and standard game language before protocol language.
5. Trust and liquidity routes should remain plainspoken and readable, not over-marketized.
