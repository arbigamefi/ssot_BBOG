# ADR-019: Multi-chain & Multi-asset readiness

**Status**: Accepted

## Context
SSOT is designed for:
- Multiple chains (Base / Arbitrum / testnets)
- Multiple assets (per-asset Bank, per-asset risk gates)

Historically, web3 frontends become unmaintainable when chain IDs, token addresses, decimals,
or module addresses are scattered across UI code.

## Decision
### Multi-chain
1) **Chain support is driven solely by embedded releases** generated by `pnpm ssot:sync`.
   - apps/web MUST NOT hardcode contract addresses.
   - The active release is selected by the connected wallet chain ID.
2) **Wagmi chain configuration is derived from `embeddedChainIds`**.
   - Only chain IDs present in embedded releases are enabled in the wallet connector.
   - A safety fallback MAY include Base Sepolia for local development prior to sync.

### Multi-asset
1) **Asset allowlist is driven solely by the embedded release manifest** (`release.assets[]`).
2) The SDK MUST treat assets as data:
   - `Hub.bankFor(asset)` is the canonical spender for approvals.
   - Token `symbol/decimals` come from the manifest when present; otherwise they are fetched
     on-demand (cached) via ERC20 `symbol/decimals` reads.

## Alternatives considered
- Hardcode a single "golden" chain and single stablecoin.
  - Rejected: creates technical debt and prevents safe multi-chain rollout.
- Allow UI to infer assets by scanning on-chain registries.
  - Rejected: not release-locked; can drift from audited release semantics.

## Consequences
✅ Multi-chain/multi-asset expansion becomes operationally safe:
- Update contract deployments → generate release bundle → `ssot:sync` → CI gates → deploy.
❗ Requires release bundles to be produced for each supported chain.
